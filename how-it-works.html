How it works

to a record.

At the door

Each classroom reader is an ESP32 with an RC522 module. It reads the card’s ID and sends it over Wi-Fi as an event — it never decides attendance itself.

In the engine

The decision engine identifies the student, finds the active lecture and applies the rules. The raw event is kept separate from the official record.

On the phone

Students, faculty, proctors and admins each see their own view update — with a reason for every result.

The rulebook

What the engine checks.

1

Card validation

A scan only counts if the card is registered to a student and is active.

2

Duplicate-scan guard

Taps inside the configured window are ignored, so a nervous double-tap never creates a second record.

3

Check-in and check-out

The first valid tap starts the session; a later tap closes it. A check-out with no check-in is flagged.

4

Duration, not just presence

Time in class is measured and compared against the minimum duration set for the lecture.

5

Late arrivals

The real arrival time is always stored, and late allowance is applied on top of it.

6

Flagged and pending review

Odd sequences are marked for review instead of being silently accepted or discarded.

7

Emergency modes

Normal, check-in only, check-out only, or manual review — switchable when hardware fails.

8

Right lecture, right room

The lecture is picked from the timetable using the terminal’s room, and labs accept only that batch.

An honest note

RFID reduces proxy attendance. It doesn’t erase it.

A card can still be handed to a friend. What Mahmoods AMS adds is traceability — timestamps, durations, flags and an audit trail — so unusual patterns are easier to spot and every decision can be explained.
